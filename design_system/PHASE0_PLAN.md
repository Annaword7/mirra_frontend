# Phase 0 — Implementation Plan (token-layer extension)

> **No source files are modified by this document.** This is the pre-flight plan for Phase 0
> only, plus a full commit plan for the phases that follow. All numbers are the exact `grep`
> totals from `DESIGN_AUDIT_EVIDENCE.md` (v2.4.0+102).

**Phase 0 definition:** *purely additive.* Introduce the complete token layer. Reference it from
**nothing** yet. Therefore: 0 replacements in feature code, 0 visual change, 0 API removal.

---

## 0. Architecture decision (LOCKED)

Two facts, confirmed with the team, settle the architecture:

1. **The app is ejected / hand-maintained** — `flutter_flow_theme.dart` is no longer regenerated by
   FlutterFlow. → Editing it in place is safe; no clobber risk. The companion-file workaround
   (former Option B) existed only to survive regeneration and is therefore unnecessary.
2. **Single light theme forever** — dark mode is explicitly not on the roadmap. → Colors never need
   to be brightness-aware, so `ThemeExtension`/lerp (former Option C) buys nothing.

**Decision: Option A — extend `FlutterFlowTheme` in place.** One API (`FlutterFlowTheme.of(context)`,
already used **1,216×**); all tokens in one file; no second lookup path.

| | A — edit in place *(chosen)* | B — companion extension file | C — ThemeExtension |
|---|---|---|---|
| One obvious API | ✅ flat/grouped on `t.` | ✅ but colors can't flip | ❌ two entry points |
| FlutterFlow conflict | ✅ none (ejected) | ✅ none | ✅ none |
| Dark mode | n/a (single theme forever) | ✗ const getters | ✅ (unneeded here) |
| Maintainability | ✅ one file, one API | ⚠ split model | ⚠ two theming systems |

Because it is single-theme forever, this also makes the **dead dark-mode plumbing removable**
(not just ignorable): the `light_dark_toggle` component, `_themeMode`/`setThemeMode`
(`main.dart:122/215`), `setDarkModeSetting` (`flutter_flow_util.dart:290`), and the `themeMode:`
argument on `MaterialApp` — see new commit 0b below.

## 5. Risks & edge cases (Phase 0)

1. **FlutterFlow re-export — N/A.** The app is ejected/hand-maintained (confirmed), so the theme
   file is never regenerated. This former top risk no longer applies; editing in place is safe.
2. **`const` correctness.** All getters return compile-time constants → no runtime cost, tree-shaken
   if unused. Edge case: `AppSpacing()` etc. must be `const` constructors (they are) so
   `const AppSpacing()` is valid.
3. **Getter-name collision with `FlutterFlowTheme`.** The extension must **not** redeclare existing
   members (`primary`, `secondary`, `success`, `warning`, `error`, `info`, `primaryText`, …) — an
   extension getter cannot override an instance member and would be silently ignored. That's why the
   semantic-hue *reassignments* (error `#FF5963→#E53935`, success, warning, `secondaryText` contrast
   fix) are **deliberately excluded from Phase 0** — they require editing the theme fields and are
   also visual changes, so they belong to Phase 1.
4. **Dual radius/spacing scales coexist** (`FFRadius.md=16` vs `AppRadius.md=12`). Acceptable while
   `FFRadius` is unused; a lint (Phase 5) will forbid new `FFRadius`/`FFSpacing` references so the
   old scale can be deleted later.
5. **Unused-symbol warnings.** Some analyzers flag unused public members; these are public API
   (intended for later phases), so no `unused_element`. Confirm `flutter analyze` stays clean.

## Answers to the five questions

**Will the public API of any widget change?**
**No.** Phase 0 adds new getters on `FlutterFlowTheme`; it removes/renames nothing. No widget
constructor, parameter, or return type changes. (The later `AppButton`/`AppInput` wrappers in
Phase 4 *add* new widgets but don't alter existing ones — and that's not Phase 0.)

**Will any visual behavior change?**
**No, in Phase 0** — the new tokens are referenced by nothing, so rendered output is byte-identical.
(Phases 1–3 introduce intended, itemized, sub-perceptual changes: one-hue semantic colors, ≤2px
spacing/radius snaps, and the `#929292→#6B6B6B` contrast fix. Those are reviewed per screen.)

**Will any snapshots, golden tests, or existing tests likely fail?**
**No.** There are **no golden/snapshot files** in the repo. The only tests are
`test/widget_test.dart` (default FlutterFlow smoke test — pumps `MyApp()`, asserts nothing about
colors) and `test/onboarding_skin_type_test.dart`; neither references `FFSpacing`, `FFRadius`,
colors, or font sizes (verified by grep). Additive Phase 0 cannot break them. Even the pixel-changing
later commits are unlikely to fail these tests since they assert behavior, not appearance.

**Will this create merge conflicts with ongoing feature work?**
**Phase 0: no** — it only adds a brand-new file, which cannot conflict. **Later refactor commits:
yes, if run now.** The working tree currently has 5 uncommitted widget files that are exactly the
refactor surface: `routine_calendar_widget.dart` (**41** literals), `search_widget.dart` (20),
`ingredient_bubbles_widget.dart` (19), `guest_prefs_sheet_widget.dart` (15),
`compatibility_result_widget.dart` (13). **Mitigation:** land the in-flight work first, and sequence
the per-file refactor commits (7–8) *after* those files are committed; refactor untouched files first.

**Can the migration be split into small independent commits?**
**Yes.** Phase 0 is a single self-contained additive commit. Every later category (colors, radius,
shadows, weight, opacity) is independent and can be one commit *per category and/or per file*, each
independently revertible with no cross-dependency except that all refactors depend on Phase 0 having
landed.
