# Воронки Mirra в Amplitude: как читать пользователей

Для менеджеров и аналитиков, которые строят графики и воронки в прод-проекте
Amplitude. Здесь только то, что нужно знать про идентификаторы и фильтры, чтобы
не считать одного человека за трёх и не строить воронку по ложному ключу.
Список событий и их свойств: `analytics_events.md`.

## Три идентификатора

| Поле | Что это у нас | У кого есть | Как читать |
|---|---|---|---|
| **User ID** | uuid аккаунта (email или Apple) | только у аккаунтов, у анонима пусто | «Аккаунт». Один аккаунт на iPhone и iPad = один пользователь |
| **Device ID** | идентичность устройства; переживает переустановку и переезд на новый телефон через бэкап | у всех | Ближайшее к «человеку». Меняется только при удалении аккаунта |
| **Amplitude ID** | внутренний id Amplitude, по нему считаются Uniques | у всех | Пока аккаунта нет = устройство. Появился аккаунт = аккаунт |

## Как Amplitude склеивает

- **Аноним → регистрация или вход.** Вся анонимная история устройства
  приклеивается к аккаунту. Воронка «установил → зарегистрировался → оплатил»
  работает по умолчанию.
- **Два аккаунта = два пользователя. Всегда.** Даже на одном телефоне, даже
  если это один человек с email- и Apple-аккаунтом. Amplitude не умеет
  объединять два User ID.
- **Выход из аккаунта.** Анонимные события после выхода уходят прошлому
  аккаунту. Другой аккаунт, зарегистрированный на этом телефоне позже, их не
  получит.
- **Удаление аккаунта.** Пользователь и вся его история удаляются из Amplitude
  (до 30 дней). Устройство получает новый Device ID, следующий аноним на нём
  новый.
- **Переустановка.** Тот же аноним: Device ID хранится в Keychain. Оговорка: в
  сборках 117 и раньше на iOS это не работало, аноним после переустановки
  становился новым.

## Что считать

| Вопрос | Как посчитать |
|---|---|
| Сколько пользователей (стандартно) | Uniques. Это аккаунты плюс анонимные устройства, не люди |
| Сколько людей | Event Segmentation → событие → Group by **Device ID** → Formula `PROPCOUNT(A)` |
| Только аккаунты | фильтр User ID is not `(none)` |
| Только анонимы | фильтр User ID = `(none)` |
| Конверсия аноним → аккаунт | событие `anon_converted`: только новые аккаунты, вход гостя в существующий не считается |

## Фильтры, без которых графики врут

- `install_source = app_store`. В прод-проект попадают и TestFlight-тестировщики,
  а покупки у них песочные. Без этого фильтра конверсия в оплату завышена.
- `app_env = Production`. Страховка от dev-сборки в сторе: такое уже было с
  билдом 108.
- `supabase_uid` есть у всех, включая анонимов. Это uuid текущей сессии, по
  нему можно найти строку в базе. Для счёта людей не использовать: у анонима
  он меняется при каждой переустановке и выходе.

## Стандартные воронки

Как собрать любую из них: Create → Funnel Analysis → шаги по порядку → окно
конверсии → сегмент с фильтрами `install_source = app_store` и
`app_env = Production` → Save в дашборд «Mirra: воронки». Воронки считают
пользователей (Amplitude ID). Анонимная история склеивается в аккаунт, поэтому
воронка с регистрацией посередине не рвётся. По устройствам воронки Amplitude
не считает, для «людей» есть рецепт в разделе «Что считать».

**Сводная: конверсия в оплату.** Какая доля новых пользователей платит.
Шаги: `[Amplitude] Screen Viewed` → `purchase_completed`. Counted as: New
users. Окно: 30 дней. Разбить по `purchase_completed.package`. Смотреть как
Conversion over time по неделям: видно, как меняется конверсия когорт.
Первый шаг именно такой, потому что это первое событие, которое есть у
каждого, кто открыл приложение, и оно идёт уже с нашим Device ID
(автособытия SDK первого запуска идут с временным, см. «Ловушки»).
Вариант за период, без когорт: Event Segmentation, A = `[Amplitude] Screen
Viewed`, B = `purchase_completed`, формула `UNIQUES(B)/UNIQUES(A)`: доля
активных за период, кто в этот же период заплатил.
Оговорка: `purchase_completed` отправляет приложение после подтверждения
покупки. Если приложение сбоит после подтверждения Apple, события не будет,
а деньги будут. Когда включена интеграция RevenueCat (см. ниже), второй шаг
лучше заменить на `rc_initial_purchase`: его шлёт сервер, он ничего не
пропускает.

**1. Онбординг.** Сколько дошли до конца анкеты.
Шаги: `onboarding_go` → `onboarding_skin` → `onboarding_skin_continue` →
`onboarding_important_continue` → `onboarding_done`. Окно: 1 день. Разбить по
`onboarding_skin.via` (`direct` / `determine`). Выходы мимо воронки:
`onboarding_skip`, `onboarding_skip_all`, `onboarding_close`.

**2. Первый разбор, активация.** Сколько нажавших сканер получили результат.
Шаги: `scan_photo_tap` → `analysis_started` → `analysis_completed`. Окно:
1 час. Разбить по `analysis_started.source` (`camera` / `gallery`). Отказы
смотреть отдельным графиком: `analysis_failed` по `reason` (`productNotFound`,
`ingredientsNotFound`, `subscriptionSync`, `unsupported`, `generic`).

**3. Аноним → аккаунт.** Какая доля анонимов заводит аккаунт.
Верхний уровень: `anon_session_started` → `anon_converted`, окно 30 дней.
`anon_session_started` срабатывает при каждой гостевой сессии: первый запуск,
после выхода, после удаления аккаунта, поэтому для новых пользователей ставьте
Counted as: New users.
Детально: `account_tap` → `create_account` → `anon_converted`, окно 1 день,
разбить по `create_account.from` (`profile` / `log_in_page`). Способ
регистрации: разбить по `anon_converted.method` (`email` / `apple`).

**4. Оплата.** Сколько открывших подписку купили.
Шаги: `premium_tap` → `paywall_offerings_loaded` → `purchase_started` →
`purchase_completed`. Окно: 1 день. Разбить по `premium_tap.from`
(`scan_limit`, `bag_add_from_card` и другие) и `purchase_started.package`.
Фильтр `install_source = app_store` здесь критичен: у тестировщиков покупки
песочные. Отказы: `purchase_failed` по `code` и `cancelled`. Отдельно следить
за `paywall_offerings_loaded` с `ready = false`: это пейвол без цен, купить
на нём нельзя.

**5. Просилка подписки.** Сколько увидевших предложение пошли в пейвол.
Шаги: `upgrade_prompt_shown` → `premium_tap`. Окно: 1 час. Разбить по
`upgrade_prompt_shown.trigger` (`first_result`, `scan_limit`,
`out_of_generations`).

**6. Косметичка и рутина.** Дошёл ли разбор до пользы.
Шаги: `analysis_completed` → `product_setting_add_bag` →
`beauty_bag_check_fit` → `routine_product_save`. Окно: 7 дней.

**Удержание** это не воронка, а Retention Analysis: стартовое событие
`onboarding_done` (или New users), возвращающее `analysis_completed`. Второй
разбор: сегмент «performed `analysis_completed` ≥ 2 times» в Event
Segmentation.

## События подписки от RevenueCat

Приходят с сервера RevenueCat, а не из приложения, поэтому видят то, чего
приложение не видит: продления, истечения, отмены автопродления, возвраты.
Несут выручку, по ним строятся Revenue-графики и LTV. Имена с префиксом `rc_`:
`rc_initial_purchase`, `rc_trial_started`, `rc_trial_converted`,
`rc_trial_cancelled`, `rc_renewal`, `rc_cancellation`, `rc_uncancellation`,
`rc_expiration`, `rc_billing_issue`, `rc_product_change`, `rc_transfer`.

- Факт первой оплаты считайте по `rc_initial_purchase`. Повторная подписка
  после истечения приходит как `rc_renewal`.
- Песочные покупки (TestFlight, Xcode) уходят в dev-проект, в проде их нет.
- У анонима событие лежит в его анонимной истории устройства без User ID, у
  аккаунта там же, где события приложения.

## Ловушки

- **Тестирование командой.** Один телефон, десять входов и выходов = десять
  «пользователей». Отсекайте `install_source`.
- **События в момент регистрации.** `log_in` (нажатие) и
  `create_profile_apple_id` уходят ещё без User ID; `anon_converted` идёт уже
  с ним. На чистом устройстве нажатия склеятся в новый аккаунт, а на
  устройстве с прошлым аккаунтом достанутся ему. Воронку регистрации считайте
  по устройствам или закладывайте погрешность.
- **Автособытия SDK.** `[Amplitude] Application Installed` и `Start Session` при
  первом запуске после установки уходят с временным Device ID. Установки
  считайте по нашим событиям онбординга, не по автособытиям.
