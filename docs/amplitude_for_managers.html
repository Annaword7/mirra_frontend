Воронки Mirra в Amplitude: как читать пользователей

Для менеджеров и аналитиков, которые строят графики и воронки. Здесь только то, что нужно знать про идентификаторы и фильтры, чтобы не считать одного человека за трёх и не строить воронку по ложному ключу. Список событий и их свойств лежит в «Карте событий Mirra».

Как Amplitude склеивает

  • Аноним → регистрация или вход. Вся анонимная история устройства приклеивается к аккаунту. Воронка «установил → зарегистрировался → оплатил» работает по умолчанию.
  • Два аккаунта = два пользователя. Всегда. Даже на одном телефоне, даже если это один человек с email- и Apple-аккаунтом. Amplitude не умеет объединять два User ID.
  • Выход из аккаунта. Анонимные события после выхода уходят прошлому аккаунту. Другой аккаунт, зарегистрированный на этом телефоне позже, их не получит.
  • Удаление аккаунта. Пользователь и вся его история удаляются из Amplitude, в течение 30 дней. Устройство получает новый Device ID, следующий аноним на нём новый.
  • Переустановка. Тот же аноним: Device ID хранится в Keychain. Оговорка: в сборках 117 и раньше на iOS это не работало, аноним после переустановки становился новым.

Фильтры, без которых графики врут

  • install_source = app_store. В прод-проект попадают и TestFlight-тестировщики, а покупки у них песочные. Без этого фильтра конверсия в оплату завышена.
  • app_env = Production. Страховка от dev-сборки в сторе: такое уже было с билдом 108.
  • supabase_uid есть у всех, включая анонимов. Это uuid текущей сессии, по нему можно найти строку в базе. Для счёта людей не использовать: у анонима он меняется при каждой переустановке и выходе.

Стандартные воронки

Как собрать любую: Create → Funnel Analysis → шаги по порядку → окно конверсии → сегмент с фильтрами install_source = app_store и app_env = Production → Save в дашборд «Mirra: воронки». Воронки считают пользователей (Amplitude ID). Анонимная история склеивается в аккаунт, поэтому воронка с регистрацией посередине не рвётся. По устройствам воронки Amplitude не считает, для «людей» есть рецепт в разделе «Что считать».

События подписки от RevenueCat

Приходят с сервера RevenueCat, а не из приложения, поэтому видят то, чего приложение не видит: продления, истечения, отмены автопродления, возвраты. Несут выручку, по ним строятся Revenue-графики и LTV.

rc_initial_purchaserc_trial_startedrc_trial_convertedrc_trial_cancelledrc_renewalrc_cancellationrc_uncancellationrc_expirationrc_billing_issuerc_product_changerc_transfer
  • Факт первой оплаты считайте по rc_initial_purchase. Повторная подписка после истечения приходит как rc_renewal.
  • Песочные покупки (TestFlight, Xcode) уходят в dev-проект, в проде их нет.
  • Кому принадлежит событие. У анонима оно лежит в анонимной истории устройства без User ID, у аккаунта там же, где события приложения.

Ловушки

  • Тестирование командой. Один телефон, десять входов и выходов = десять «пользователей». Отсекайте install_source.
  • События в момент регистрации. log_in (нажатие) и create_profile_apple_id уходят ещё без User ID; anon_converted идёт уже с ним. На чистом устройстве нажатия склеятся в новый аккаунт, а на устройстве с прошлым аккаунтом достанутся ему. Воронку регистрации считайте по устройствам или закладывайте погрешность.
  • Автособытия SDK. [Amplitude] Application Installed и Start Session при первом запуске после установки уходят с временным Device ID. Установки считайте по нашим событиям онбординга, не по автособытиям.
